## 0. "Neon is our DB — so why does Cloudflare/AWS come into this at all?"

A fair question, and an important distinction: **a database and object storage do two
different jobs, and you need both.** They are not competitors.

| | **Neon (Postgres)** — a *database* | **Object storage (R2 / S3)** — a *file store* |
|---|---|---|
| Built for | structured rows: ids, status, text, numbers, URLs | large binary files (blobs): PNG, MP4, PDF |
| Good at | querying, joins, transactions, relationships | storing/serving big files cheaply over a CDN |
| Bad at | holding multi-MB binary blobs | querying or relating data |
| In our case | the generation record, status, copy, cost, **the URL pointing at an image** | **the actual pixels/frames of that image/video** |

**Why not just put the image bytes in Neon?** You technically *can* (a `bytea` column), but it's
the wrong tool: it bloats the DB, makes every backup huge and slow, costs far more per GB, has no
CDN, and — critically — you can't hand a `<img src>` / WhatsApp / Meta a *database row*. Those
consumers need a **URL to a file**. So images/videos do not belong inside Postgres.

**The standard pattern (and what your repo already does):**
```
Neon row:   { id, status, copy, cost, asset_url: "https://…/ad_01.png" }   ← the POINTER
Bucket:     ad_01.png  (the actual 1.6 MB of pixels)                       ← the BYTES
```
apps/api today only ever stores third-party provider **URLs** as text — it never stores bytes in
the DB. Our pipeline is the first thing that *generates its own* bytes, so it needs its own place
to put them. **Neon stays the database** (it now holds the metadata + the URL, already built in
the DB layer). The bucket is *only* for the heavy binary files.

**Why a new vendor at all?** Because right now those generated bytes only live on the ai-layer's
ephemeral disk (wiped on every redeploy). To make the stored URLs durable, the bytes need a
permanent home. Three ways to give them one:

1. **Cloudflare R2 / AWS S3** — purpose-built object storage, CDN, cheap. The proper answer.
   Adds one vendor. (R2 has no egress fees, which matters when clients/WhatsApp/Meta repeatedly
   refetch the same creative.)
2. **A Railway volume** — you already deploy on Railway; a persistent volume is disk that
   survives redeploys. The ai-layer writes there and serves the files. **No new vendor**, but:
   tied to that one service, no CDN, and you manage capacity/backups yourself.
3. **Do nothing** — keep the ephemeral approach; accept that asset URLs break on redeploy.

The rest of this doc plans option 1/2 (the code is identical for R2 and S3; a Railway volume is a
small variant that skips the bucket and serves from disk).

## The shape

The ai-layer generates the bytes locally (it already downloads provider URLs immediately
because they expire). It should **upload each finished asset to an S3-compatible bucket
and return the durable public URL** in the job. apps/api then stores that URL directly —
no proxy hop needed.

```
ai-layer pipeline -> writes ad_NN.png / video.mp4 locally
   -> storage.upload(file, key="creative/<job>/<file>") -> PUBLIC bucket URL
   -> job.assets[].url = bucket URL
apps/api -> stores the bucket URL as-is in studio_outputs.asset_url
web/WhatsApp/Meta -> load the bucket URL directly (no /api proxy)
```

**S3-compatible** means the same code (boto3) works for **Cloudflare R2** or **AWS S3** —
the only difference is the endpoint + the public URL base.

## What gets built

1. **`ai_layer/storage.py`** — `upload(local_path, key) -> str | None`. Uses `boto3`
   against the configured S3-compatible endpoint; returns the public URL, or `None` when
   storage isn't configured (feature-gated on `STORAGE_BUCKET`).
2. **Wire into the service** — after a run, upload the shippable assets (per-format ad
   PNGs, the video MP4, the logo, and the winner refs) and set their URLs to bucket URLs.
   **Fallback:** when storage is off, keep today's behavior (ai-layer static mount + the
   apps/api proxy) — so nothing breaks until a bucket is configured.
3. **apps/api** — make the URL handling mode-aware: a `http(s)://…` bucket URL is stored
   as-is (browser loads it directly); an ai-layer-relative `/creative/assets/…` path is
   proxied as today. One-line change to the `proxy()` helper.
4. **Config / env** (new, ai-layer side): `STORAGE_BUCKET`, `STORAGE_ENDPOINT`,
   `STORAGE_KEY`, `STORAGE_SECRET`, `STORAGE_REGION` (R2 = `auto`), `STORAGE_PUBLIC_BASE`
   (the public/CDN base for the bucket, e.g. an R2 public bucket URL or a custom domain).
5. **Dep:** add `boto3` to the ai-layer `pyproject.toml` (lazy-imported).
6. **Key layout:** `creative/<job_id>/<filename>` — groups a run's assets; the job_id
   (uuid) makes keys unguessable.
7. **Tests:** mock the S3 client (no live bucket needed); assert upload is called with the
   right key + the returned URL flows into the job. Plus the off/fallback path.

## Decisions (need your call — also asked interactively)

1. **Provider** — Cloudflare R2 (recommended: S3-compatible, no egress fees, cheap, easy
   public buckets) vs AWS S3 vs you already have one.
2. **URL access** — public bucket URLs (recommended: WhatsApp/Meta/HTML must fetch the
   asset externally, and ad creatives are meant to be shared; keys are unguessable) vs
   presigned/expiring URLs (more locked-down, but they expire and complicate sharing).
3. **Which assets to upload** — just the finished ads + video (smallest), or also the
   logo, backgrounds, brand-kit, and pulled Meta winners (full run archive).

> Build approach: feature-gated, additive, fallback preserved, on the same branch.
